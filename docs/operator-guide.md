# Codex Mission Control Operator Guide

## Purpose

Codex Mission Control is an Azure DevOps and repo-rule-aware AI development control plane.

It is not a replacement for each developer's local Codex. The App controls the workflow by creating Request IDs, dispatching Agent0-3 packets to each developer's local Codex worker, collecting artifacts, reading Azure evidence, applying repo rules, and guarding limited PR writes.

The main screen is login-first, then request-first. Ordinary users first complete the `連線設定` dialog to connect their local Codex worker and select a worker-reported project. Until that is complete, request input, request records, workflow status, and stage progress are not shown. After connection is complete, the dialog closes and the main screen keeps only a compact local connection summary. Worker command templates, Azure diagnostics, and queue-wide operations are intentionally not part of the ordinary flow.

## Team Workflow

Primary route:

```text
Request Intake
-> Agent0 Dispatch
-> Agent1 Source & Scope
-> Agent2 Controlled Implementation
-> Agent3 Review & Delivery
-> PR Ready
-> human-approved / verified Azure PR
-> PR Created / Tracked
```

Workflow stages are persisted in the server-side SQLite database under `.control-plane/`. This directory is ignored by Git.

Each request stores:

- Request ID.
- Owner.
- Assigned local Codex worker.
- Request kind and Task Level.
- Request detail as intake evidence.
- Agent run packets and returned artifacts.
- Audit events.
- Linked PR traceability records.

Request detail is not a confirmed specification. Agent1 must still verify sources and stop on missing or conflicting evidence.

## Local Worker Companion

Each developer installs the Windows Local Launcher once on their own machine. The launcher listens only on that developer's `127.0.0.1:17320`, stores the worker profile with Windows DPAPI, and starts `scripts/local-worker.mjs` as a background local process.

The launcher downloads a worker manifest from `/api/workers/bootstrap?file=worker-manifest.json` before starting the worker. It writes worker files into a temporary download directory, verifies the SHA-256 hash for `local-worker.mjs` and `local-worker-utils.mjs`, then replaces the local worker cache. The worker reports its version, script hash, launcher version, and update time in repository and run heartbeats. If the App detects a hash mismatch, it blocks dispatch with a worker-version message instead of treating it as an Agent source blocker.

The worker uses:

- The developer's local repository path.
- The developer's own Codex CLI, invoked by the worker through a default `codex exec` command.
- The developer's worker token.
- The Agent Packet generated by the App.
- Optional `AZURE_DEVOPS_PAT` from the developer's DPAPI-protected local launcher profile.
- Optional `CONTROL_PLANE_AUTO_COMMIT_PR=1` when the developer allows the worker to prepare the request branch, commit, push, and let Azure Repos expose the team PR.

The App uses runtime config to set the worker `CONTROL_PLANE_URL`. In local development this resolves to `http://localhost:3000`. In deployed team environments, set `CONTROL_PLANE_PUBLIC_URL` to the canonical App URL so every developer's local launcher starts workers that poll the shared Control Plane instead of a developer's localhost.

The worker returns:

- Agent artifact.
- Command output.
- Git status / diff summary.
- Completion, failure, or blocked status.
- Agent0 request interpretation, when the command output or artifact includes the control-plane interpretation markers.

The App can stop a local worker connection by disabling the worker token. When the Local Launcher is available, the UI also asks it to stop the background worker and delete the DPAPI-protected profile so a Windows login restart cannot reconnect. Stop is blocked while an Agent task is queued or running.

The ordinary UI does not expose worker command templates. By default, the worker builds its own command from the selected sandbox mode:

```text
codex exec --skip-git-repo-check --sandbox <workspace-write|danger-full-access> - < {packetFile}
```

`workspace-write` is the default. The ordinary UI labels `danger-full-access` as complete local access and requires explicit user confirmation because it gives Codex broader local filesystem access. The worker must report Codex readiness before the App opens the request workflow. A worker heartbeat alone is not enough.

Codex readiness requires a terminal-callable Codex CLI. The Codex Desktop executable under WindowsApps is treated as a desktop-internal executable, not as a valid Local Worker executor. When readiness fails, the App shows the diagnostic category and executable path if detected. With the Local Launcher installed, the setup action opens a visible PowerShell on the user's machine, runs the worker setup-only flow, installs Codex CLI when missing, starts `codex login` for the human login step, and then restarts the background worker. The App does not install packages or log in from the browser or the server process.

The formal Local Launcher install mode is a Windows Scheduled Task. If Windows denies Scheduled Task creation, the installer may temporarily start the launcher through the current user's Startup folder so the session can continue, but it records `temporary-startup-folder` and tells the UI that Administrator PowerShell is required to finish the formal Scheduled Task install.

The App registration form does not store a user's Azure PAT. The PAT input is only shown when the user allows the local worker to prepare commit and draft PR. When a PAT is entered, it is sent only to that user's Local Launcher and stored in the DPAPI-protected local profile; the server still stores no PAT value.

The auto commit / draft PR checkbox is a user preference for the Local Worker flow. It does not allow merge PR, abandon PR, deploy, branch policy mutation, Work Item field mutation, or any Azure write that fails the control-plane guarded write policy.

Repository discovery and Codex readiness are reported by the local worker started by the user's Local Launcher. The App does not scan the user's filesystem from the browser or depend on server-side directory scanning for the ordinary repository dropdown. `scripts/local-worker.mjs` scans candidate user folders on the developer's machine and posts repository candidates plus `codexReady / codexStatus / codexError / codexDiagnosticCode / codexExecutablePath` to `/api/workers/repositories`. When the user selects a repository from the worker-reported dropdown, the App saves that path on the worker record. Creating a request snapshots the selected repository onto the Request ID, and each queued Agent run stores the same repository snapshot so Agent0-3 execute in the original selected project even if the worker later switches to another repository.

Worker runtime failures are separated from Agent blockers. Script hash or version mismatch is shown as `本機 Worker 版本不同步`; missing internal functions and worker-side `ReferenceError` failures are shown as `Worker 內部錯誤`. In both cases the user updates/restarts the Worker, then retries the same Agent. Dirty repo and merge-conflict blockers are shown as repo-state blockers with the affected git status, not as missing requirement evidence.

Agent0 / Codex should include the following block in its output so the App can update request metadata from the Local Worker instead of relying on the provisional browser preview:

```text
CONTROL_PLANE_INTERPRETATION_START
{
  "title": "short human-readable title",
  "kind": "REQ | BUG | REF | DOC | OPS",
  "taskLevel": "Level 0 | Level 1 | Level 2 | Level 3",
  "summary": "classification summary; do not claim sources are confirmed",
  "suggestedNextAgent": "agent1",
  "missingSources": ["Spec / business rule confirmation"],
  "sourceWarnings": ["User text is intake evidence only"],
  "riskFlags": [],
  "guardrails": ["Do not invent requirements."]
}
CONTROL_PLANE_INTERPRETATION_END
```

## PAT Scopes

Read checks require:

- Code Read
- Pull Requests Read
- Work Items Read
- Build Read

Guarded writes require:

- Pull Requests Read & write
- Work Items Read & write, only when linking an existing Work Item to a PR

Not required for the MVP:

- Build execute
- Release
- Test Management
- Packaging
- Deploy
- Merge
- Branch policy mutation

## Normal Workflow

1. Optionally allow the local worker to prepare commit and draft PR; only then does the Azure PAT field appear.
2. Install the Windows Local Launcher once if the App cannot reach `127.0.0.1:17320`.
3. Start the local connection from the App. The App registers a worker, sends the one-time worker token to the user's Local Launcher, and the launcher stores it with DPAPI before starting the background worker.
4. Wait for heartbeat, Codex readiness, and project candidates from the worker.
5. Select the local project from the dropdown after the worker reports candidates.
6. After connection is complete, create a request by typing the natural-language need and selecting the delivery mode.
7. The App shows a provisional local preview and queues Agent0 to the assigned local Codex worker.
8. Local Codex returns the authoritative workflow interpretation for this request.
9. The App automatically continues Agent0 -> Agent1 -> Agent2 -> Agent3 until a blocker, human decision, PR Ready, or delivered state is reached. Agent2 is where local project code changes are made; Agent3 reviews the implementation result, diff, and verification evidence. Manual retry controls are recovery-only and live under the technical log details, not in the normal workflow.
10. Connect Azure DevOps with a PAT only when Azure evidence or guarded PR writes are needed.
11. Run Delivery Gate for active PRs.
11. Use Azure 單號 candidate search if the Delivery Gate reports a missing linked Work Item.
12. Link an existing Azure Boards Work Item when the correct Azure 單號 is known. The App reads the Work Item first so the confirmation dialog can show its title, type, state, and iteration.
13. Use guarded write actions only when the operator intentionally wants to publish PR metadata:
   - Create draft PR.
   - Update PR description marker block.
   - Post readiness comment.
   - Link existing Work Item.
14. When the request uses PR delivery, the App automatically discovers the active Azure PR for the pushed request branch and records it for traceability. Manual PR ID entry remains a fallback only.

## Delivery Modes

Each request stores a delivery mode:

- `draft_pr`: the default team delivery mode. Agent2 works from `origin/develop` on `feature/{workItemId}`, `bug/{workItemId}`, or `hotfix/{workItemId}` when a verified Azure Work Item is linked. Agent3 completion moves the request to PR Ready, then the App discovers and tracks the active Azure PR before the request is marked PR Created / Tracked.
- `no_pr`: for personal project changes or work that does not need PR publication. Agent0 through Agent3 still run, Agent3 still reviews the result, and the App marks the request delivered after Agent3 completes.

The workflow does not create, merge, abandon, approve, deploy, or update Azure PRs. It prepares and pushes the request branch, then reads Azure Repos to track the PR that appears for that branch.

## Natural-Language Request Intake

Request Intake captures a user's request as intake evidence before an Agent thread is opened.

The normal user-facing input is only the request text. The App shows a provisional preview, then local Codex returns the workflow interpretation:

- Request kind: `REQ`, `BUG`, `HOTFIX`, `REF`, `DOC`, or `OPS`.
- Request title.
- Task Level.
- Missing source signals.
- High-risk operation signals.
- Optional Azure PR or Azure 單號 reference when the text includes a recognizable reference.

The generated Request ID uses:

```text
<KIND>-<YYYYMMDDHHmm>-<slug>
```

Legacy Request Intake records are stored only in browser local storage under:

```text
azure-ai-control-plane.requestIntake
```

The team workflow stores new request records in the server-side SQLite database. Request Intake does not write Azure DevOps state. Request detail is not confirmed Spec, Figma, Swagger/API, QA, or implementation scope. Agent0 and later agents must treat it as intake evidence only and stop when sources are missing or conflicting.

The browser-side preview is deterministic and does not require an OpenAI API key. The authoritative interpretation comes from local Codex when Agent0 completes. Neither source may confirm requirements; both may only classify, flag missing sources, and flag high-risk operations.

## Request Records And Stage Gate

After local worker login, the ordinary UI only shows:

- Compact local Codex connection state.
- New request input.
- My request records.
- Workflow status for the selected request.

The local worker setup and project dropdown live in the `連線設定` dialog. The dialog opens automatically until connection, Codex readiness, and project selection are complete; after that, users can reopen it from the compact settings button.

Global success, error, copy, and setup messages appear as bottom-right fading toasts. Long-lived blocking states remain inside the connection dialog or the selected request status panel.

The App evaluates workflow status automatically and refreshes selected request progress in the background. The Workflow Status panel shows the current Agent, worker heartbeat, elapsed time, and latest update. A background activity banner appears while a request is queued or running. Terminal output remains available in the technical log details after the worker returns it. Normal users do not need to manually refresh or continue the workflow; `重新同步狀態` and `重試派發下一個 Agent` exist only as advanced recovery controls. The Stage Gate expands operational detail only when attention is needed:

- Missing worker.
- High-risk request signal.
- Worker failed or blocked.
- Azure PR write approval required.
- No automatic next workflow step.

## Guarded Writes

Every Azure write must pass both UI confirmation and server-side validation.

Testing-stage write policy:

- Only PRs whose source branch is under `AITraining/*` may use Azure write actions.
- All other branches are read-only in the App, even if the PAT has write scopes.
- `AI_Training/*` remains a recognized test branch for rule classification, but it is not writable during this testing stage.

Formal PR delivery branch policy:

- Team delivery branches are `feature/{workItemId}`, `bug/{workItemId}`, or `hotfix/{workItemId}`.
- The target/base branch is `develop`.
- These branches are used for local git commit/push and Azure PR discovery. They do not allow the App to merge, abandon, approve, deploy, or mutate Work Item fields.
- The `{workItemId}` must come from a verified Azure Work Item read. A number parsed only from request text is a tracking reference and must not derive the formal PR branch.
- Branch names use only the kind and Work Item number. Do not add title, slug, date, or other suffixes.

Allowed MVP writes:

- Create PR from non-protected source branch to protected target branch.
- Update active PR description with the control-plane marker block.
- Post active PR readiness comment with the control-plane marker.
- Link an existing Azure Boards Work Item to an active PR.

Before linking a Work Item, the App must read that Work Item and show its identifying fields in the confirmation dialog. If the Work Item cannot be read, the link write should stop.

Candidate search is read-only. It uses PR branch, title, and description context to infer possible Work Item IDs, then reads Azure Boards metadata for display. Selecting a candidate only fills the link input.

PR traceability is verified before it changes workflow state. The App first tries to discover an active Azure PR whose source branch is the request branch and whose target branch is `develop`. A verified link may move `PR Ready` to `PR Created`, but it does not merge, abandon, deploy, or update Work Item fields. Manual PR ID entry is only a fallback when discovery is delayed or ambiguous.

Blocked or deferred:

- Abandon PR.
- Merge PR.
- Approve review.
- Update Work Item content, state, assignee, or fields.
- Create Work Items.
- Change reviewers.
- Create or delete branches.
- Trigger builds or deployments.
- Change branch policies.

## Rule Checks

Delivery Gate evaluates active PRs.

Historical Audit evaluates all loaded PRs and marks completed or abandoned PRs as historical evidence, not current delivery gates.

Rule checks use:

- Source branch and target branch.
- Linked Work Item evidence.
- Build evidence and PR statuses.
- Reviewer evidence.
- Changed files.
- Repo rule sources.
- Path gates for contracts, docs, i18n, environment shape, Azure policy, and route/shell behavior.

Reviewer evidence is read-only in the MVP. The App may display reviewers and votes, but it must not add reviewers, remove reviewers, approve, reject, or reset votes.

AI training test branches:

- `AITraining/*`
- `AI_Training/*`

These are treated as test branches that target `develop`.

Only `AITraining/*` is writable during the testing stage. `AI_Training/*` is display and rule-check evidence only unless the product policy changes.

Formal team branches:

- `feature/{workItemId}`
- `bug/{workItemId}`
- `hotfix/{workItemId}`

These are treated as request delivery branches that target `develop` and are used for automatic PR discovery, not Azure PR creation.
`hotfix/{workItemId}` is recognized for branch naming, but its production release target policy remains pending until the release flow is finalized.

## Agent Packet

Agent Packet is the structured handoff artifact for short-lived AI threads.

It includes:

- Request ID.
- Recommended next Agent role.
- Startup prompt.
- Confirmed Azure evidence.
- Scope and Non-Scope.
- Stage gate result.
- Blockers.
- Human decisions.
- Required verification.
- Changed files.
- Stop conditions.

Agent Packet does not execute Codex, modify local repositories, or write Azure DevOps state. Packets are role-specific: Agent0/Agent1 receive intake evidence and source-check rules, while Agent2/Agent3 primarily receive compact prior handoff summaries, diff/test evidence, and the minimum stop rules needed for their stage. Agent1 must return fixed Source Check Report fields for confirmed requirements, confirmed scope, allowed files, non-scope, do-not-touch areas, blockers, can-proceed status, and the Task Package for Agent2. Agent2/Agent3 packets extract only those structured fields, flag missing required fields as incomplete handoff, and fall back to a clipped excerpt only when an upstream artifact is unstructured.

## Local Audit Records

The App keeps local, non-secret audit records:

- Write Activity.
- Rule Check History.
- Request Intake records.

These records do not contain PAT values. They can be cleared from the UI.

## Local Verification

Use local checks before trusting a change:

```text
pnpm test
pnpm lint
pnpm build
pnpm smoke
```

`pnpm smoke` does not require a PAT for local checks. If `AZURE_DEVOPS_PAT` is set, it also performs read-only Azure overview checks. The smoke script must not perform Azure writes.

## Stop Conditions

Stop and ask for human decision if the next step requires:

- Azure write not covered by the MVP.
- New Azure permission scope.
- Requirement or rule change.
- Env modification.
- Package installation.
- Deployment.
- File deletion.
- Large refactor.
- Shared core module modification.
- Product decision such as hotfix target policy.
